# `@deepseek-ai/dsh-work-shell`

This private Profile Bundle adds the DeepSeek Harness Desktop App shell to the official DSH Web Profile. The official `@deepseek-ai/dsh-web-app` runtime and `@deepseek-ai/dsh-web-frontend` keep ownership of the server, transport, Client graph, and boot lifecycle. This Bundle disables the official `ui-layout`, `ui-sidebar`, `ui-conversation`, and duplicate `ui-settings-general` page shells, then contributes the visible root while retaining the official Client services and all other Profile plugins.

The root, sidebar, conversation, and General settings entries register in one lifecycle effect, parent first and dispose child first. The product renders standard settings sections, `shell.overlay`, `sidebar.footer.action`, the whole-column `details` seat, the product `agent.workbench.tool` list, and fourteen additive conversation seats. `ui-conversation` must remain disabled because the Slot registry correctly rejects two parent entries declaring the same child protocol.

The conversation adapter maps header actions, input overlay and docks, plan and model controls, assistant actions, turn tails, and the `conversation.composer` Chain into the existing product page. The product textarea supplies the standard per-Session `useInput` and `inputActions` kit. Official reference, consume-token, command-claim, and insert-text events update that same draft with revision checks. The separate `@deepseek-ai/dsh-client-product-commands` Bundle owns the lifecycle-bound `dsh-work` input source for `/new`, `/runs`, and `/trace`; `/model`, `/compact`, Skills, and other official commands remain owned by their Profile plugins. The separate `@deepseek-ai/dsh-client-product-references` Bundle owns the App file and conversation sources in the same official registry; this Shell exposes only the Session-fenced `dshWorkProductReferences` catalog and does not own source matching or candidate UI.

The Profile-owned `@deepseek-ai/dsh-client-ui-skill` package is the only Skill catalog and selection authority in the formal Client. Its `skill` input source calls `skill.list` for the bound Session and inserts the literal `/<name> ` reference into the shared draft. The product Skill picker is not mounted while this Client Host is present.

The official model and Plan plugins occupy their named seats and remain the only writers for the bound DSH Session. The permission plugin decorates `/permission` through the shared command overlay. The Goal plugin reads the Session projection in `conversation.input.dock` and owns its Remote mutations. The product does not keep duplicate model, Plan, permission, Goal, or command catalogs in the formal Client host; standalone development keeps only the minimum local fallbacks needed without that host.

The visible product Queue and compact Plan and permission readouts subscribe to the same official Client Session: Queue data comes from `ConversationSnapshot.queue`, while Plan and permission values come from `session.projections.faceOf(...)`. The App protocol stream only resolves the App conversation to its DSH Session and carries product message content that has not yet moved to official Chat; it is not a second state authority. Standalone development still projects its protocol snapshot because no Client Session exists there.

The shell dispatches the official `conversation.composer` Chain with the bound Session snapshot and its pending interactions. The existing product composer remains mounted as the all-decline resident surface, so drafts survive; when a selector accepts, the elected Client Plugin temporarily replaces it. The official `ui-question` flow therefore owns question rendering and answers through its `PendingWait` Remote. A formal Client turn declares this interaction ownership to the desktop runtime, which prevents the older server question bridge from consuming the same DSH request a second time. Third-party Chain contributions use the same dispatch without package-specific App code.

The shell publishes the official `IConversation` service contract from a lifecycle-bound service adapter. Cross-Plugin value imports are forbidden by the Client Loader, so the shell does not import the implementation from `ui-conversation`; its service delegates send, Queue updates, cancel, and older-history loading directly to the addressed DSH Session. Its Session input resolver and composer-block registry are backed by the same product draft projection, so Client plugins can wait for and call the standard service instead of depending on an App-only bridge. The official Agent Preset plugin consequently owns the header label and the new-session `conversation.hero.agentPreset` chip beside the product Workspace picker. The root-scoped hero seat renders before the Session-scoped conversation guard because it chooses the composition before a Session exists. Product file attachments still use the desktop attachment adapter; this service integration does not claim that the product composer has adopted the official browser draft-image registry.

The shell also publishes the narrow `dshWorkProductActions` Client service. It contains no command catalog or matching rules and only fences dispatch by the currently selected Session before calling the product handler. Cordis rebinds a Service to the caller plugin Context, so cross-plugin dependencies use ordinary TypeScript private properties rather than JavaScript `#private` brands. Desktop action plugins can therefore be installed, disabled, or replaced through Profile composition without importing shell code or operating on product DOM.

The shell publishes the narrow observable `dshWorkProductSearchMode` Client service for the currently selected Session. It projects the App-owned web policy and routes cycle requests back to the product draft; the separate `@deepseek-ai/dsh-client-product-search-mode` Bundle owns the visible control in `conversation.input.left`. The service is a desktop adapter because this turn policy is carried by the App protocol rather than an official Session projection.

The shell publishes the narrow observable `dshWorkProductWorkspaces` Client service for the current product workspace catalog and explicit selection, folder onboarding, and creation actions. The separate `@deepseek-ai/dsh-client-product-workspaces` Bundle disables the default `ui-workspace` provider before it occupies the root-scoped single `conversation.hero.workspace` seat. The formal Client therefore has one picker and one state owner; replacing the Bundle through the Profile frees the same standard seat for another reviewed provider.

The shell publishes the Session-fenced `dshWorkProductAttachments` display projection and one opaque-id removal action. The separate `@deepseek-ai/dsh-client-product-attachments` Bundle owns the visible list through the explicit root extension `dsh-work.composer.pre-session` before the first Session exists and through the standard `conversation.input.dock` Slot after a Session is bound. It reuses the official `AttachmentRail` atom for images and never receives local paths or bytes. The desktop Host remains the draft authority because the official Web controller does not expose its browser `File` registry through `IConversation`.

The shell also declares the official keyed `conversation.chat.node` seat for Tool calls. Live events and cold history retain the same DSH `ToolCallBlock`, and each product Tool row routes that block through the Profile-owned `@deepseek-ai/dsh-client-ui-tool` plugin before using the existing product row as its all-decline fallback. The official Tool plugin then owns the nested keyed `tool.call.toolview` seat, so an installed community plugin can replace one wire Tool name without changing the App or replacing the whole conversation page. Inspecting that row stores only its Session and call identities, opens the existing product right column, and dispatches the same block into `conversation.details.tool`; the Profile-owned Tool plugin remains responsible for terminal, read, search, web, diff, and generic output rendering. In rc.6 the independent Tool plugin still reads a Tool-only subset of the `conversation` locale namespace that is registered inside the disabled page shell. This Bundle registers exactly that published zh/en subset through the shared Locale service and releases it with the Shell lifecycle; it does not copy Conversation state or claim support for the rest of the page-shell dictionary.

Assistant actions use finalized DSH message ids, while turn-tail contributions prefer the official Session timeline and keep the product turn id separate. Official produced-file actions open the current Files workbench. A Client Plugin that owns `details` renders in the existing right column and controls it through the shared `layout` adapter. The Models route renders the official Models settings section. Theme and locale state come from the shared DSH Client services; App storage is only a standalone fallback.

General message-body Chat Nodes and browser-owned image identities remain unsupported until they can reuse one product state owner. The Plugin Center therefore reports `conversation.chat.node` as partial with only the `tool-call` key, while Workspace Hero, the Composer Chain, input Overlay, Plan, Model, Agent Preset, `conversation.details.tool`, and nested `tool.call.toolview` seats are fully mapped. The package is the App-managed desktop shell, not a portable feature plugin for an unmodified official Web surface. Portable product features must ship as separate DSH Bundles and pass the official-Web interoperability gate.
