# `@deepseek-ai/dsh-work-shell`

This private Profile Bundle adds the DeepSeek Harness Desktop App shell to the official DSH Web Profile. The official `@deepseek-ai/dsh-web-app` runtime and `@deepseek-ai/dsh-web-frontend` keep ownership of the server, transport, Client graph, and boot lifecycle. This Bundle disables the official `ui-layout`, `ui-sidebar`, `ui-conversation`, and duplicate `ui-settings-general` page shells, then contributes the visible root while retaining the official Client services and all other Profile plugins.

The root, sidebar, conversation, and General settings entries register in one lifecycle effect, parent first and dispose child first. The product renders standard settings sections, `shell.overlay`, `sidebar.footer.action`, the whole-column `details` seat, the product `agent.workbench.tool` list, and thirteen additive conversation seats. `ui-conversation` must remain disabled because the Slot registry correctly rejects two parent entries declaring the same child protocol.

The conversation adapter maps header actions, input overlay and docks, plan and model controls, assistant actions, turn tails, and the `conversation.composer` Chain into the existing product page. The product textarea supplies the standard per-Session `useInput` and `inputActions` kit. Official reference, consume-token, command-claim, and insert-text events update that same draft with revision checks. The App-only `/new`, `/runs`, and `/trace` actions are one lifecycle-bound `dsh-work` input source; `/model`, `/compact`, Skills, and other official commands remain owned by their Profile plugins.

The official model and Plan plugins occupy their named seats and remain the only writers for the bound DSH Session. The permission plugin decorates `/permission` through the shared command overlay. The Goal plugin reads the Session projection in `conversation.input.dock` and owns its Remote mutations. The product does not keep duplicate model, Plan, permission, Goal, or command catalogs in the formal Client host; standalone development keeps only the minimum local fallbacks needed without that host.

The shell dispatches the official `conversation.composer` Chain with the bound Session snapshot and its pending interactions. The existing product composer remains mounted as the all-decline resident surface, so drafts survive; when a selector accepts, the elected Client Plugin temporarily replaces it. The official `ui-question` flow therefore owns question rendering and answers through its `PendingWait` Remote. A formal Client turn declares this interaction ownership to the desktop runtime, which prevents the older server question bridge from consuming the same DSH request a second time. Third-party Chain contributions use the same dispatch without package-specific App code.

The shell also declares the official keyed `conversation.chat.node` seat for Tool calls. Live events and cold history retain the same DSH `ToolCallBlock`, and each product Tool row routes that block through the Profile-owned `@deepseek-ai/dsh-client-ui-tool` plugin before using the existing product row as its all-decline fallback. The official Tool plugin then owns the nested keyed `tool.call.toolview` seat, so an installed community plugin can replace one wire Tool name without changing the App or replacing the whole conversation page.

Assistant actions use finalized DSH message ids, while turn-tail contributions prefer the official Session timeline and keep the product turn id separate. Official produced-file actions open the current Files workbench. A Client Plugin that owns `details` renders in the existing right column and controls it through the shared `layout` adapter. The Models route renders the official Models settings section. Theme and locale state come from the shared DSH Client services; App storage is only a standalone fallback.

General message-body Chat Nodes, hero replacement, the official conversation-owned `conversation.details.tool` child, and browser-owned image identities remain unsupported until they can reuse one product state owner. The package is the App-managed desktop shell, not a portable feature plugin for an unmodified official Web surface. Portable product features must ship as separate DSH Bundles and pass the official-Web interoperability gate.
