# DSH Desktop 社区发行版转型方案

日期：2026-08-20

状态：本文件是发行版转型的完整实施依据。没有通过对应退出条件的能力不得写成已完成。

## 1. 最终结论

DSH Desktop 是基于 DeepSeek Harness 构建的独立社区桌面发行版。

这个仓库的核心产品不是一套自研前端，而是一个方便普通用户下载和使用 DSH 的桌面发行包。它把官方 Runtime、官方 Web、Electron 原生宿主和多个经过真实验证的官方或社区插件组合在一起。用户不需要先理解 Node、pnpm、Profile 或 Bundle 才能开始对话和使用默认插件。

项目继续使用 Electron，不迁移到 Rust 或 Tauri。Electron 只负责窗口、托盘、更新、系统协议、文件选择、原生浏览器工作区和受控系统权限；Agent、Session、模型、工具、插件和主界面由官方 DSH 提供。

产品结构固定为：

```text
Installer artifact plane
        +-- official DSH Runtime and Web
        +-- embedded package manager
        +-- pinned reviewed plugin tarballs
        +-- source, permission, license and hash BOM
        |
        | fresh Profile initialization or explicit user action only
        v
DSH Profile state plane
        +-- official base and web bundles
        +-- installed official and community bundles
        +-- DSH Desktop portable bundles
        +-- narrow desktop adapter bundles
        |
        v
Official dsh-web-app inside a thin Electron Native Host
```

DSH Profile 是运行时插件状态的唯一权威。应用不维护第二份插件数据库，不用 Renderer 本地存储推断安装状态，也不建设与官方并行的插件生命周期。

发行包必须同时包含已解析的官方产物、固定哈希的精选插件 tarball、受控包管理器、来源与许可清单以及验证记录。新安装在无网络时也应能通过官方插件命令初始化 Profile，启动官方 Web 和全部随包且默认安装的插件。已存在的 Profile 在启动和更新时只读；应用不因精选清单变化而重写其 Bundle 列表或用户 patch。

## 2. 项目身份与上游关系

| 项目 | 约定 |
|---|---|
| 产品名 | `DSH Desktop` |
| GitHub 仓库 | `vibeinging/dsh-desktop` |
| 项目描述 | 基于 DeepSeek Harness 构建的社区桌面发行版 |
| 应用标识 | `com.vibeinging.dsh-desktop`，各平台在同一命名空间下派生 |
| 安装包前缀 | `dsh-desktop` |
| 自研 npm scope | 维护者自有 scope，默认使用 `@vibeinging/*` |
| 官方 npm scope | `@deepseek-ai/*` 只用于官方 SDK、运行时和官方 Bundle |

官方权威只包括：

- `deepseek-ai/deepseek-harness` 仓库。
- 官方 `@deepseek-ai/*` npm 包。
- 官方文档、Profile、Bundle、Host 和 Client 契约。

`anywhere-labs/deepseek-harness-desktop` 是与我们并列的独立社区发行版。它可以作为架构和产品参考，但不是官方桌面实现，也不是我们的上游。我们不复制它的品牌、更新地址、网站、发布服务或产品代码。

公开页面可以准确说明与 DeepSeek Harness 的兼容关系，但不得把完整商标作为项目名，不得暗示官方背书、合作或授权。项目继续使用 [MIT License](../../LICENSE)；免费发布是本项目自己的发行策略。

## 3. 上游依赖与仓库策略

### 3.1 默认只使用官方 npm 产物

自研插件只能基于官方 npm SDK 开发：

- DSH 包同时声明为 peer dependency 和开发依赖。
- 不使用 `file:`、`link:` 或 `workspace:` 指向 DSH 源码。
- TypeScript `paths`、`extends` 和 `references` 不得指向 DSH checkout。
- 不修改官方源码解决应用问题。
- 官方运行时、SDK 和构建产物由 lockfile 固定。

### 3.2 官方源码只能作为可选只读输入

默认仓库不需要 DSH submodule。只有离线构建、源码审查或定位官方产物问题确有需要时，才允许加入只读 submodule，并同时满足：

- submodule 指向 `deepseek-ai/deepseek-harness`。
- 主仓库记录上游仓库、固定提交和对应 npm 产物。
- 插件构建仍从 npm SDK 解析，不从 submodule 解析。
- 禁止修改 submodule，禁止把补丁保存在 submodule 中。
- 禁止把官方完整 Git 历史导入主仓库。
- submodule 不参与主仓库 Contributors 归属，也不成为运行时状态权威。

如果 npm 产物能够支持开发、测试和打包，就不引入 submodule。

### 3.3 上游同步

每次更新官方依赖只做一项变更：

1. 更新 lockfile 中的官方依赖。
2. 重新生成或核对上游来源记录。
3. 运行 Profile、Session、Client 图、模型设置和插件安装回归。
4. 记录不兼容点和删除的临时适配代码。

上游更新不得与主界面迁移、权限重构、社区插件接入或产品发布混在同一提交中。

## 4. 目标运行结构

### 4.1 Electron Native Host

Electron 主进程只持有无法由普通 Web 或 DSH 插件安全完成的能力：

- 窗口、标题栏、托盘和系统通知。
- 应用更新、安装包和系统协议。
- 原生文件与目录选择。
- 原生 Browser Workspace、下载和网页权限。
- DSH 子进程启动、停止、健康检查和退出清理。
- 经过白名单约束的桌面服务。

Electron 不持有 Chat、Session 队列、插件安装列表、模型配置或业务页面状态。

### 4.2 DSH Runtime and Profile

DSH Runtime 持有：

- Agent、Session、模型、工具和审批。
- Host 服务和 Client 连接。
- Profile Bundle 组合。
- 插件安装、卸载、启停和配置。
- Session 事件、历史回放和投影。

应用展示的插件状态必须来自 Profile 和实际运行图。

### 4.3 Official Web Client

官方 `dsh-web-app` 是唯一 Web 宿主和基础界面，拥有：

- Chat 和 Session 历史。
- 工具调用与结果展示。
- 审批、问题和队列交互。
- 模型设置。
- 插件管理。
- 基础布局、侧边栏和设置页面。

DSH Desktop 不再维护第二套 Chat、首页、设置和插件中心。产品独有页面通过标准 Client Bundle、Slot 或路由贡献进入官方 Client 图。

[`dsh-web-ui`](https://github.com/zhu1090093659/dsh-web-ui) 是首选社区 UI 候选来源，通过 Profile 挂到官方 Client 图。它不是第二套 Renderer，也不取代官方 Session 和 Chat 协议。应用只选择通过审查的子包，不把社区源码复制进自有 Renderer。

### 4.4 上游桌面能力复评

当前公开上游提供 `base`、`headless` 和 `web-app` Bundle，没有可直接采用的官方 Desktop Bundle。本方案不把等待或验证一个尚不存在的 Bundle 设为实施阶段；当前主线固定为官方 `dsh-web-app` 加薄 Electron 宿主。

上游以后发布桌面 Bundle 或公开对应能力时，再单独复评重复插件 id、config 覆盖、Host 服务所有权、Client roster 和原生权限边界。可替代的过渡适配器必须在同一项变更中删除重叠实现。

## 5. 能力分层与安全边界

| 形态 | 用途 | 可以访问 | 不可以访问 |
|---|---|---|---|
| Native Host | 窗口、更新、系统协议、原生浏览器工作区、进程监督 | Electron 和操作系统 API | 业务页面状态、第三方任意调用 |
| Host Bundle | DSH 服务、工具、会话扩展和 Profile 生命周期 | Cordis Context 与声明的 DSH 服务 | Electron 原始对象、未声明 IPC |
| Client Bundle | 页面、Slot、主题 token 和交互组件 | DSH Client 注入服务和 Slot | Node、preload、文件系统、任意命令 |
| Desktop Adapter | 把一项原生能力收窄为可审核服务 | 明确方法、参数、权限和生命周期 | 通用 IPC、任意路径、任意 shell、任意 JavaScript |

`desktop-shell` 只是架构层级。只有具备 Bundle patch、Cordis 生命周期、明确服务契约和完整卸载清理的实现，才可以称为 DSH 插件。

### 5.1 Web 权限

- 官方 Web 所在 webContents 不注入 `window.electronAPI`。
- 官方 Web 不开启 Node integration，不开放远程模块或通用 IPC。
- 第三方 Client Bundle 不能取得 Electron 对象。
- 可信原生页面可以使用独立、最小的 preload，但不得与第三方 Client 插件共用执行环境。
- 桌面能力必须通过声明的窄 Host 服务使用。
- 原生调用必须检查 Session、Profile、权限和目标资源，不能只信任前端传入路径。

### 5.2 Browser Workspace

Browser Workspace 保留为 Electron 原生能力，因为 `WebContentsView`、下载、权限、截图和网页进程隔离属于可信宿主职责。

普通 iframe 或 Web 预览插件可以与 Browser Workspace 同时存在，但不能冒充其权限边界。官方 Web 中只显示标准 Slot 和状态；原生 webContents 的创建、销毁和权限仍由 Electron 持有。

## 6. 插件契约

### 6.1 Profile Bundle

可通过官方插件命令安装并自动进入 Profile 层的包，必须在 `package.json` 中声明：

```json
{
  "dsh": {
    "bundle": {
      "patch": "./cordis.patch.yml"
    }
  }
}
```

`cordis.patch.yml` 按稳定插件 id 插入、替换或禁用 Cordis 行。后层覆盖前层时，目标行的 config 按官方 patch 语义处理，不能假设深合并。

### 6.2 Client Bundle

带浏览器界面的包在 `package.json` 的 `dsh.client` 中声明浏览器半边，并提供 `./client` 导出。`dsh.client` 不会单独让包进入 Profile。

一个可直接安装的 UI Bundle 通常同时具备：

1. `dsh.bundle.patch`，把 Host 和 Client 行挂入 Profile。
2. `dsh.client`，声明浏览器半边。
3. `./client`，提供浏览器构建产物。
4. Cordis inject，等待真正依赖的服务。

`dsh.client.inject` 只用于依赖信息和预检，不决定激活顺序。

### 6.3 可移植性等级

| 等级 | 定义 | 发布要求 |
|---|---|---|
| `portable` | 只依赖公开 DSH Host 和 Client 服务 | 必须在纯官方 Web Profile 和 DSH Desktop 各完成安装、启动、停用和卸载 |
| `desktop-adapter` | 依赖 DSH Desktop 的窄 Host 服务 | 必须声明服务依赖、缺失时失败方式和桌面权限 |
| `desktop-native` | 仅 Electron 宿主内部使用 | 不进入普通插件市场，不伪装成可安装 Client 插件 |

### 6.4 npm 身份和发布

- 自研公开包统一使用维护者自有 scope。
- 现有自研包不得使用官方 scope 对外发布。
- DSH 依赖声明兼容范围，发布输入固定到 lockfile 解析结果。
- 外部 Bundle 固定到可复现来源，不依赖浮动分支或移动 tag。
- tarball 哈希和 lockfile 必须来自真实安装产物。
- 安装脚本、原生依赖、网络访问和进程权限必须进入审查记录。

### 6.5 发行态插件产物

发行包不用复制源码目录或建立解析链接来冒充插件安装。每个随包插件都必须产生一个已构建、可离线安装的固定 tarball，并在精选清单中记录包名、锁定结果、来源、SHA-256、许可、权限、默认状态和验证证据。

安装包同时携带固定的 pnpm 运行时。该运行时只进入 DSH 插件命令子进程的 `PATH`，不修改系统环境，不要求用户预装 Node 或 pnpm。随包 tarball 在首次需要时先校验哈希，再复制到 DSH 数据目录中的稳定本地插件库；Profile 中的依赖不指向可能随应用更新变化的安装目录。

新 Profile 中的默认插件通过官方 `dsh plugin --profile` 命令从本地 tarball 离线安装。只有包含已构建运行入口、不需要未审查安装脚本的插件才可随包。用户后续安装的网络来源仍走同一条官方命令和预检链路，不因发行包有本地插件库而绕过安全审查。

## 7. Profile 是唯一插件权威

Profile 负责：

- Bundle 安装、卸载、启停和排序。
- 插件配置和 patch 组合。
- 官方、社区和用户插件。
- 当前运行实例实际加载的 Host 和 Client 图。

应用不得：

- 用 `localStorage` 保存权威插件列表。
- 用自建数据库复制 Profile 状态。
- 用构建清单覆盖用户安装、卸载或停用选择。
- 在启动时静默禁用发生冲突的插件。
- 通过复制包文件冒充安装完成。

产品名、图标、安装包和新 Profile 默认值继续由构建配置管理。发行包只维护一份可审计的精选插件清单，并由它生成随包 tarball 列表、新 Profile 安装输入、第三方公告、权限摘要和测试预期。这份清单是产物平面的唯一数据源，但不是运行状态。

启动和更新规则固定为：

1. Profile 不存在时，先在隔离目录初始化官方 Web Profile，再使用本地 tarball 和官方插件命令安装默认插件；全部成功后才将其发布为正式 Profile。
2. Profile 已存在时，启动路径只读取并验证 manifest、patch 和最终运行图，不重排 Bundle，不删除未审查项，不补回默认项。
3. 应用更新只能把新 tarball 加入本地插件库并显示更新建议，不自动改变已有 Profile 中的插件及其锁定结果。应用新的 DSH Runtime 前必须预检当前有效图；如果已安装插件不兼容，用户必须明确选择更新插件、延后应用更新或使用安全 Profile。新权限或新网络、进程能力必须再次请求用户确认。
4. 安装、更新和卸载操作按 Profile 串行执行，只有官方命令成功且最终运行图可加载后才对用户报告完成。
5. 冲突或启动失败只生成诊断和恢复选项，不静默修改原 Profile。

本方案中的插件术语固定为：

| 术语 | 权威含义 |
|---|---|
| 随包产物 | 安装包或稳定本地插件库中有固定 tarball，不表示已进入 Profile |
| 已安装 | Profile 依赖和 Bundle 列表由官方命令成功更新，包可被最终图解析 |
| 已启用 | 插件贡献存在于最终 Cordis 和 Client 图中 |
| 已停用 | 插件可仍是 Profile 依赖，但后置 patch 或明确配置使其贡献不激活 |
| 已卸载 | 官方命令已从 Profile 依赖和 Bundle 列表移除该插件；安装包中的 tarball 可仍作为可重装产物存在 |

随包插件分为三种状态：

| 状态 | 安装包 | 新 Profile | 已有 Profile |
|---|---|---|---|
| 随包且默认安装 | 包含固定 tarball | 通过官方命令离线安装 | 不自动补装，用户可停用或卸载 |
| 随包但可选 | 包含固定 tarball | 不安装 | 用户确认权限后可离线安装 |
| 插件目录候选 | 不包含 | 不安装 | 用户通过官方 Profile 安装 |

精选清单不得在启动或更新时覆盖现有用户 Profile。用户已卸载或停用的随包插件不得被静默恢复；新增精选插件对已有用户只显示为可安装建议。本地插件库只在确认没有任何 Profile 依赖相应 tarball 时才可清理旧产物。

### 7.1 启动失败恢复

Electron 必须监督 DSH 子进程、Host 健康和 Client 启动结果。Profile 解析失败、插件抛错、Client 图无法激活或官方 Web 在受限时间内未就绪时，不可留下空白窗口，也不可静默改写原 Profile。

失败时只打开一个最小 Electron 本地恢复页。它不包含 Chat、首页或插件市场，不加载第三方 Client，只展示失败阶段、Profile 路径、可安全公开的错误摘要和以下明确操作：

- 不改数据重试原 Profile。
- 使用独立安全 Profile 启动纯官方 `base` 和 `web-app`，不改原 Profile。
- 对用户选中的可卸载插件执行官方移除命令，或打开 Profile 文件供用户手动修复。
- 导出去除凭据、环境变量和用户内容后的诊断包。

安全 Profile 是诊断表面，不是第二套产品 Profile，不存储日常用户选择。恢复页必须记录最近一次失败的阶段和处理结果，防止无限重启循环。

## 8. dsh-web-ui 桌面安全候选组合

项目取消自研主题包和自研主题选择。Web 视觉交给官方 Theme 服务与 `dsh-web-ui` 的皮肤中心；没有选择社区皮肤时，保持官方默认外观。Electron 只持有标题栏、原生窗口背景和窗口透明度，不再向 Web 提供自研主题 API。

`dsh-web-ui` 是一个社区插件集合，不是单个主题。它的聚合包通过 `dsh.bundle.patch` 插入 Host 和 Client 行，不覆盖官方 Chat 行；有公开 Slot 的能力优先使用 Slot，部分侧边栏、面板和皮肤仍依赖 DOM 属性兼容层。这层兼容逻辑由社区项目维护，DSH Desktop 不复制、不分叉、不把它变成应用私有 Renderer 代码。[`Better Sidebar`](https://github.com/dsh-external/DSH-better-sidebar) 是聚合包引用的独立外部项目，必须单独记录来源、契约、许可和回归证据，不能只继承聚合包的审查结论。

本节的分类是候选顺序，不是预先批准的默认清单。一个子包只有通过官方能力重叠比较、固定 tarball 审查、干净 Profile 安装、真实 Electron 交互、断网重启和卸载恢复后，才可从“候选”晋级为“随包且默认安装”或“随包但可选”。

发行配置不直接安装 `@linxin666/dsh-web-ui-all`。该聚合包会同时带入桌面启动与关机、插件管理、远程入口、SSH、视觉端点、Agent 预设、定时任务、右侧面板和皮肤资产，与 Electron 生命周期、官方插件管理和安全默认值的边界不同。聚合包只能用于独立兼容性实验，不是发行前的必过门槛；发行 Profile 只按独立子包的证据做决定。

| 分类 | `dsh-web-ui` 能力 | 发行策略 |
|---|---|---|
| 首批候选 | Better Sidebar、Chat recovery | 先比较官方侧边栏、继续和重试能力；通过独立 Bundle 验证后再决定默认状态 |
| 资产审查阻塞 | 皮肤中心 | 审查每份内建资产的许可条款与来源；未通过前只使用官方外观 |
| 后续低权限候选 | 任务看板、Git 图谱、Skill 浏览器、社区目录和宠物 | 逐包审查；只有通过后才可作为随包可选插件 |
| 用户主动安装 | 远程 Web、SSH、图像理解和 Agent 预设 | 安装前明示网络、进程、凭据、本地文件和模型行为变化 |
| 不进入发行 Profile | 桌面启动器、旧 AionUi 右栏、社区插件管理器 | 分别与 Electron 启停、Better Sidebar 和官方插件管理重复 |

皮肤资产可以拥有独立许可条款。只有许可条款、署名、素材来源和再分发条件全部通过审查的资产才能进入安装包；未通过的皮肤不随应用分发。

## 9. 附件和多模态边界

不能假设 DSH 基础内容块、Session、provider adapter、压缩和官方 UI 已经完整支持图片或音频。

接入附件前必须验证完整链路：

1. 输入块类型能够由公开 DSH 契约表达。
2. Session 可以持久化并回放。
3. provider adapter 能正确发送给目标模型。
4. 压缩和历史投影不会丢失内容。
5. 官方 UI 能显示输入、失败和历史。

没有完整证据时：

- 不宣称原生多模态。
- 不把附件路径拼入文本。
- 文件通过明确资源引用或工具访问。
- 图片处理作为独立工具或受控桌面适配能力。

## 10. 社区插件采用策略

插件精选、组合、验证和随安装包交付是本仓库的核心工作，不是发行前的附加任务。应用可以随包交付多个已验证插件，但“已验证”必须有当前官方 Runtime、当前桌面 Profile 和真实 Electron 的证据，不能只看 README、下载量或源码结构。

功能来源按以下顺序决定：

1. 官方 DSH 已有：直接使用官方实现。
2. 社区已有且契约合适：审查后通过 Profile 安装。
3. 官方和社区都没有：开发独立 Bundle。

采用社区插件前记录：

- 仓库、npm 包、固定来源和许可证。
- DSH 兼容范围和构建方式。
- 安装脚本、原生依赖和网络访问。
- Host、Client 和桌面权限。
- 数据目录和卸载行为。
- tarball 体积、安装包增量、冷启动、Client 激活和存储成本。
- provider、插件 id、路由和 Slot 冲突。
- 在候选 Profile 中的安装、启动、停用、卸载和重启结果。

`dsh-web-ui` 是已选定的首选 UI 候选来源，不是已批准的默认组合。Better Sidebar 由聚合包依赖的独立外部项目提供，与 Chat recovery 一样需要单包审查。`dsh-native-memory`、OpenPencil 和其他社区项目仍是候选。每个子包的采用结论必须来自当前依赖下的真实测试。

应用不建设第二套插件市场状态。插件发现优先使用官方插件管理和经过审查的社区目录；项目可以维护精选目录元数据，但安装动作和最终状态必须回到官方 Profile。

每次公开发行都在发行报告中记录官方 Web 基线和每个随包插件的体积、冷启动、Client 激活与存储增量，并在当次发行前固定接受预算。没有基线、增量和预算结论的候选插件不得晋级为随包插件。

每个随包插件必须单独有评估记录和回归入口。一个插件出问题时，用户应能通过第 7.1 节的恢复页启动安全 Profile，再停用或卸载它，而不是让整个应用白屏。

### 11.1 数据处理边界

可以直接删除：

- 旧项目挂载记录。
- 旧 Renderer 的本地插件列表。
- 本地队列权威和兼容迁移代码。
- 已被官方或社区插件替代的私有页面状态。

- DSH Profile 和用户安装选择。

## 12. 分阶段实施

### 阶段 0：身份、边界和基线

任务：

- 统一产品名、仓库名、应用标识和社区项目描述。
- 清除官方背书暗示和社区项目的品牌、更新地址。
- 确认 Electron 保留，Rust 和 Tauri 不在本次范围。
- 写明 Profile 是插件状态唯一权威。
- 建立现有自研包的 owner、等级和处置结论。
- 建立精选插件清单的数据结构、证据字段和 Profile 生成边界。
- 记录当前构建、测试、Profile、安装包体积、冷启动、Client 激活、存储和真实 Electron 基线。

退出条件：

- 全仓不再把完整商标作为项目名。
- 自研公开包计划不再使用官方 scope。
- 关键错误明确失败，不静默降级。
- 精选清单可生成新 Profile 的安装输入和第三方公告，但不能覆盖已有 Profile。
- 基线证据可以在干净环境复现。

### 阶段 1：Profile 权威与离线插件基础

任务：

- 删除启动、状态查询和插件安装后自动重写 `dsh.profile.bundles` 的逻辑，不再用硬编码允许列表静默隔离用户 Client。
- 建立唯一精选插件清单，生成随包 tarball、新 Profile 安装输入、权限摘要、第三方公告和测试预期。
- 在安装包中携带固定 pnpm 运行时，只把它注入 DSH 插件命令子进程。
- 建立 DSH 数据目录中的稳定本地插件库，复制前校验 tarball 哈希。
- 在隔离目录中通过官方命令原子初始化新 Web Profile；已有 Profile 的启动路径只读。
- 串行化安装、更新和卸载，命令失败或最终图无法加载时不报告成功。
- 在应用新 DSH Runtime 前预检当前有效图；已安装插件不兼容时，只提供更新插件、延后应用更新和安全 Profile 三类明示选择。

退出条件：

- 新用户在断网和无系统 Node、pnpm 的环境中可初始化官方 Web Profile 和默认插件。
- 用户停用或卸载插件后，重启和应用更新不会恢复它。
- 新精选插件对已有 Profile 只产生建议，不产生状态变更。
- DSH Runtime 更新不会静默改变已安装插件的锁定结果，不兼容结果可以在真实更新流程中阻止应用。
- 打包清单、Profile 初始化、法律公告和测试没有重复手写的插件名单。

实施状态（2026-08-20）：阶段 1 的 Profile 权威、精选清单、固定 tarball、受控 pnpm、稳定本地插件库和原子新 Profile 初始化已完成源码与 Profile 集成验证；当前精选默认值只包含 7 个 Host/portable/desktop-adapter Bundle，不包含自研 Shell、主题包、旧产品 Client UI 或工作台页面。源码检查、单元测试、官方 npm Profile 集成和发行准备已通过，真实 Electron 首启、断网安装包和应用更新回归仍是后续验证门，不在本状态中提前宣称完成。

补充状态（2026-08-20）：应用更新安装前已经加入当前 Profile 和官方 `--dump-config` 只读预检；预检失败不会写入待安装记录或调用安装退出，恢复分支明确保留“更新插件、稍后更新、安全 Profile”。

### 阶段 2：官方 Web 成为唯一主界面

任务：

- 停止 `dsh-work-shell` 对官方布局、侧边栏、对话和设置的替换。
- Electron 主窗口承载官方 `dsh-web-app`。
- dump 官方 `base` 和 `web-app` 组合后的 Cordis 配置，检查重复插件 id、config 覆盖、Host 服务所有权和 Client roster。
- 删除重复 Chat、首页、设置和插件中心路由。
- 删除 `dsh-theme-pack` 及与它绑定的首页、设置和 Renderer 状态。
- 暂时关闭尚未迁移的自研 UI，允许功能短期减少。
- 独有导航和桌面入口改成标准 Slot contribution。
- 启动真实 Session，验证历史、模型设置、审批、队列、工具事件和过渡适配器的 Session 绑定。

退出条件：

- 新 Session、历史、工具事件、审批、队列、模型设置和插件管理均使用官方页面及协议。
- 没有旧首页或兼容界面作为隐藏回退。
- 真实 Electron 交互和截图证明用户看到官方 Web 基线。
- 最终 Profile 层次和插件图有可复现证据，没有重复 provider 或隐式覆盖。

### 阶段 3：收窄 Electron 权限

任务：

- 从官方 Web 所在 webContents 移除产品 preload。
- 盘点全部 IPC 调用者，删除旧 Renderer 专用和无调用通道。
- 必须保留的能力改为 Desktop Adapter 服务。
- 路径、下载、进程、窗口和更新能力增加来源与权限检查。

退出条件：

- 官方 Web 中不存在 `window.electronAPI`。
- 第三方 Client 插件无法取得 Node、Electron 或通用 IPC。
- Browser Workspace、文件选择、更新和窗口操作通过窄服务工作。
- 越权路径、未知 Session 和未授权调用被拒绝。

### 阶段 4：建立启动失败恢复

任务：

- 从 DSH 子进程、Host 健康和 Client 启动链路中产生可判定的失败阶段。
- 实现最小 Electron 本地恢复页，不加载 Chat 和第三方 Client。
- 实现独立安全 Profile，只加载官方 `base` 和 `web-app`，不修改原 Profile。
- 提供重试、用户确认的插件移除、打开 Profile 和隐私过滤后的诊断导出。
- 记录最近失败阶段和处理结果，阻止无限重启。

退出条件：

- 破坏一个候选 Client Bundle 不会留下白屏，用户可进入纯官方 Web 安全 Profile。
- 恢复过程不静默改写原 Profile，诊断包不包含凭据和用户内容。
- 官方 Web 自身也无法启动时，恢复页能显示错误并停止自动重试。

### 阶段 5：证明双向插件兼容

任务：

- 选择一个依赖少、权限窄的自研 portable Bundle，通过官方插件命令安装到纯官方 Web Profile。

- 验证安装、启动、Client 激活、配置、停用、卸载和重启。

退出条件：

- 我方 portable Bundle 不依赖 Electron、应用私有路径或硬编码注册。
- 社区 Bundle 通过官方 Profile 机制运行。
- 两边都没有第二套安装状态。
- README 只记录真实验证过的命令和结果。

## 13. 插件冲突与安全预检

| 检查 | 失败条件 |
|---|---|
| 来源 | 仓库、npm 或 tarball 不能解析到固定来源 |
| 兼容范围 | peer dependency 不包含当前 DSH 运行时 |
| Bundle 声明 | 可安装 Bundle 缺少有效 `dsh.bundle.patch` |
| Client 声明 | 声明 `dsh.client` 但缺少 `./client` 输出 |
| 安装脚本 | 存在未审查的生命周期脚本或原生二进制 |
| Host 权限 | 请求通用 shell、任意路径、任意进程或未声明网络能力 |
| Client 权限 | 依赖 preload、Node、Electron 或非公开全局变量 |
| Provider | 与已有 provider、插件 id、路由或 Slot 所有权冲突 |
| 产品重复 | 复制官方 Chat、首页、设置或插件中心且无独立价值 |
| 桌面生命周期 | 社区插件可自行创建启动器、结束 Host 或绕过 Electron 退出流程 |
| 资产许可 | 皮肤、插图、字体或音视频缺少可再分发依据 |
| 体积和启动成本 | tarball、安装包增量、冷启动或 Client 激活超过当前发行预算 |
| 卸载 | effect、事件、路由、Slot、服务或观察者不能完整释放 |

同 id 的 Profile patch 可能是有意覆盖，不能一律当成错误。预检必须区分明确覆盖、重复 provider 和无法释放的并存实现。

预检通过不等于正式采用。外部 Bundle 仍需在候选 Profile 中完成真实安装、启动、停用和卸载。

| Electron 用户体验 | 真实 Electron 启动和当前页面截图；浏览器测试不能代替 |
| 启动恢复 | 破坏插件、Profile 解析失败、Client 超时、安全 Profile、无静默写入和隐私过滤诊断 |
| 安装包 | 干净用户目录 smoke、断网首启、Profile 创建、更新、用户卸载保留和恢复 |
| 性能与体积 | 每个随包插件的 tarball 体积、安装包增量、冷启动、Client 激活和存储增量 |

报告必须区分源码检查、单元测试、构建、Profile 集成、真实 Electron 和安装包验证。低一级证据不能替代高一级结论。

## 15. 实施护栏

1. Electron 保留，但只承担原生宿主职责。
2. 官方 DSH Runtime、Profile 和 Web 是产品底座。
3. Profile 是插件状态唯一权威。
4. 不导入官方完整 Git 历史，不修改官方源码。
5. 插件只基于官方 npm SDK 开发。
6. 官方 Web 拥有 Chat、首页、设置、插件中心和基础布局。
7. 官方 Web 没有通用 preload、Node 或 Electron 权限。
8. 功能来源顺序是官方、社区、自研。
9. 自研公开包使用维护者自有 scope。
10. 项目不维护自研主题包；Web 外观由官方 Theme 服务和经审查的 `dsh-web-ui` 皮肤资产提供。
11. 插件冲突显式预检，不静默禁用其他插件。
12. 没有纯官方 Profile 和真实 Desktop 双向证据，不写“完全兼容”。
13. 没有真实 Electron 或安装包证据，不写“已完成桌面适配”。
14. 不使用社区项目的品牌、更新地址或官方身份叙述。
15. `dsh-web-ui` 只通过 Profile 选包进入应用，不复制源码，不直接安装聚合包。
16. 社区 DOM 兼容层每次跟随官方 Web 更新做真实界面回归，不把源码检查当成兼容证据。
17. 精选插件清单是发行构建输入，Profile 是用户运行状态权威，两者不能互相冒充。
18. 新增随包插件不对已有用户强制安装，用户已停用或卸载的插件不在更新后自动恢复。
19. 启动和状态查询只读已有 Profile，任何状态变更都需要明确用户操作或新 Profile 初始化。
20. 随包插件只通过固定 tarball、受控 pnpm 和官方插件命令进入 Profile。
21. 插件启动失败进入明示恢复页，不白屏，不静默切换或修改原 Profile。

## 16. 完成标准

只有同时满足以下条件，才能宣布发行版转型完成：

- 主窗口使用官方 `dsh-web-app`，没有第二套 Chat、首页、设置和插件中心。
- 官方 Web 没有 Electron preload、Node 或通用 IPC。
- Profile 是插件状态唯一权威。
- 已有 Profile 的启动、状态查询和应用更新不重写用户 Bundle 列表或 patch。
- 新用户下载一个安装包后，无需系统 Node、pnpm、npm 登录或首启网络下载即可进入官方 Web。
- 精选清单能生成安装包中的固定 tarball、本地安装输入、权限摘要、第三方公告和测试预期，不存在并行手写名单。
- 至少一个我方 portable Bundle 在纯官方 Web Profile 完整安装和卸载。
- 至少一个 `dsh-web-ui` 独立子包通过完整门槛并由官方 Profile 安装；所有晋级为随包的子包均完成启停、配置、卸载和重启回归。
- 自研公开包全部使用自有 scope，并声明 portable 或 desktop-adapter。
- Browser Workspace 等原生能力通过窄服务工作，越权测试通过。
- 自研 `dsh-theme-pack` 和主题本地状态已删除，未选社区皮肤时官方外观可正常使用。
- 桌面启动器、旧 AionUi 右栏和社区插件管理器未进入发行 Profile。
- 随包分发的皮肤资产全部具有可核对的许可条款和来源。
- 精选插件清单可复现安装包内的每个插件产物，并且不会覆盖用户 Profile 选择。
- 一个失败插件不会让主窗口白屏，用户可在不改原 Profile 的前提下启动安全 Profile 并完成恢复。
- README 的命令、截图和兼容声明来自真实验证。
- 公开名称、描述和素材符合商标与非背书边界。

## 17. 当前执行顺序

下一批开发按以下顺序进行：

1. 完成身份、scope、当前运行图和脏工作区基线。
2. 删除启动时 Profile 重写，建立精选清单、固定 tarball、受控 pnpm 和离线新 Profile 初始化。
3. 建立零自研 UI 的官方 Web 基线，接受暂时功能减少。
4. 移除官方 Web 的产品 preload，收窄原生服务。
5. 建立恢复页和只含官方 `base` 与 `web-app` 的安全 Profile。
6. 用一个自研 portable Bundle 和一个社区 UI 候选 Bundle 证明双向安装。
7. 删除 `dsh-theme-pack`，审查 Better Sidebar、Chat recovery 和后续 `dsh-web-ui` 子包，只晋级通过门槛的包。
8. 按处置矩阵逐包恢复真正有价值的功能。
9. 最后完成皮肤资产许可审查、插件目录、真实截图和公开发行。

每完成一个阶段或一个独立包，更新本文档对应状态并单独提交。实现与本文档冲突时先停止开发，确认是文档错误还是实现越界，不以临时代码形成新的架构事实。
